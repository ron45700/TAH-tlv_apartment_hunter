## The calls

- **Posts:** 19 pending canonicals from the store, chosen by crude patterns for the hard cases,
  plus #45's case from `data/raw/test_posts.json` (20). The patterns mislabelled two: the posts
  picked as "seeking" and "Jaffa" turned out to be sale posts, and every setting classified them
  `for_sale`.
- **Settings**, two passes each over the 20: effort `none` with temperature omitted
  (`none_default`); effort `none` with temperature 0 (`none_t0`); effort `low` (`low`, no
  temperature, ASSUMPTIONS O4).
- **Every call:** the Responses API (`client.responses.create`), `store: false`, the instructions in
  a developer message with an explicit cache breakpoint at its end and
  `prompt_cache_options.mode: "explicit"`, the post's text alone in the user message,
  `max_output_tokens` 4,000, a strict JSON schema derived from the pydantic response model by the
  SDK (`type_to_text_format_param`). One first-version prompt, in English with Hebrew examples, not
  tuned (saved as `instructions.txt`).
- **The key** was read from the environment by the script and never printed or logged.
- **The tier:** no call was refused; nothing was worked around.

## 1. The schema

**Accepted unchanged.** The schema the SDK derived from the approved `ListingExtraction`
(`SCHEMA.md`) passed strict mode on the first call, with ten `$defs` (the generic `Marked[T]` gives
one definition per type), `anyOf` for the nullable values and for `int` or `"included"`.
**No change was made to the response model**: no name and no shape differs from what Ron approved.
120 of 120 answers parsed and validated against the model.

- **Temperature 0 is not deterministic:** under `none_t0` one post's `post_nature` changed between
  the passes (the shared post: `rental_offer`, then `not_listing`), and 6 of 20 posts differed in
  some field.
- **`post_nature` otherwise agreed in all six runs on all 20 posts.** #45's case came out
  `seeking` in all six.
- **Against `none_default` pass 1,** `low` pass 1 differed most (furnished 4, rooms 3, price 3,
  area names 3, entry date as written 3, broker 2, arnona, balcony); `none_t0` pass 1 differed in
  area names 3, entry date as written 2, streets, balcony, parking, broker. Which answers are right
  is for the review page and the regression set: this spike did not judge accuracy.
- **Caching:** the prefix of 2,514 tokens (the instructions and the schema) was written once and
  then read on every call. It survived the change of temperature (`none_t0` wrote nothing); the
  change to effort `low` wrote it once more. The post itself was never written to the cache: no
  call wrote more than the prefix.

## 7. Recommendation — for Ron, not decided

**Effort `none` with temperature 0**, provisionally, confirmed or changed on the regression set.
*Why:* it was the cheapest and the fastest, and its two passes agreed most (14 of 20 posts
identical, 98.3% of fields); `low` cost about 50% more, took 5 seconds a call, and did not agree
better. Temperature 0 is not deterministic either, so the regression set should run each setting
twice before the choice is final. `low` stays the fallback if `none` misses the bar (#148).

## 8. Found, for later tasks

- **Area names come back with Hebrew prefix letters, as written:** the Old North came back as
  "בצפון הישן" ("in the Old North"). The translation table cannot match it as is: the lookup key
  (#135) has to handle the prefixes (ב, ה, ל, מ, ו and combinations), or the table has to hold the
  prefixed forms. Task 2.3; for Ron.
- **The cached prefix includes the schema:** 2,514 tokens for about 4,800 characters of
  instructions plus the schema. A schema change costs one cache write, about $0.0003.
- **A cut answer is billed:** an `incomplete` response costs its input and output with nothing
  usable. With `max_output_tokens` at 4,000 against answers of at most 784 tokens, none occurred.
